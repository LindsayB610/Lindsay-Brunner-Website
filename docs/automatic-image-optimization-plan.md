## Outcome

New local raster images receive web delivery variants automatically. Authors supply an image and normal layout semantics, not a compression command. Production builds reject uncovered image paths rather than silently shipping them. Coverage includes Hugo content, raw HTML, standalone pages, React, and JavaScript-driven galleries. Original artwork and downloadable files remain intact.

## 2. Add one shared derivative generator

Use the existing Sharp dependency behind a reusable module and CLI. Keep source files untouched. Generate stable source-path/policy/width/format derivative URLs plus a manifest mapping each source and policy to dimensions, format, bytes, and variants. Content hashes identify the disposable transform cache, not public URLs. Hash source bytes, transform options, and encoder version; use deterministic ordering and bounded concurrency. Use `.cache/image-optimization/` for disposable transform cache, `.generated/images/manifest.json` for the pre-Vite manifest, and `public/_img/` for published derivatives. Neither intermediate directory may live in `assets/react` or `public`. Ignore intermediate directories in Git. A clean build must generate current derivatives with no transform cache. Publish the fixed supported width ladder for every current eligible source; compatibility and revalidation semantics are specified in section 6.

Use a candidate width ladder of 320, 480, 640, 800, 1200, 1600, and 2400, capped at source dimensions. Generate only widths needed by the established display profiles; do not automatically multiply every asset by seven widths and two formats. Measure cold-build duration, peak memory, derivative count, and disk usage against the existing build before fixing the final profiles. Generate WebP plus compressed JPEG/PNG fallback; preserve alpha, orientation, and color appearance. Never enlarge or crop by default. Select a smaller valid encoding, retaining an already-efficient original where appropriate. Use lossless profiles for diagrams/screenshots where text fidelity requires them; do not force lossy WebP on every image. Defer AVIF until measured value justifies added build time.

Separate delivery from identity: OG URLs, favicon files, full-resolution download/zoom links, and original source files stay intact. An image used both as OG art and a visible header still receives visible-page derivatives. Animated images must preserve animation or have a documented exception, never silently become a still frame. SVG stays vector. External or user-supplied runtime images need an explicit delivery policy; do not fetch arbitrary URLs during builds.

## 3. Connect every rendering surface

Preparation discovers the complete eligible local source universe in `static/` and Hugo page bundles before rendering, with external and non-delivery assets explicitly classified. The initial implementation processes eligible raster assets independent of whether a reference scanner can find them, avoiding a circular dependency on final HTML. Generated OG files are available first. Dynamic build-generated assets must be registered as producers before this step. Late unregistered assets fail with their producer/reference location; they never silently pass through. A fixture referenced only by standalone HTML must work on a clean build.

Order production builds as: existing OG generation, image preparation/manifest, React compilation, Hugo rendering, structural transformation of remaining built HTML, final derivative copy, then validation. Keep existing OG behavior isolated; the new processor itself must not mutate author assets. Verify this order against existing build contracts before changing commands.

- Hugo: shared responsive-image partial used by the Markdown render hook, templates, and shortcodes.
- React: shared image component imports generated manifest data before Vite runs. Update dynamic image consumers and gallery data adapters; do not rewrite compiled JavaScript strings. Hugo fallback and React must use the same profile, sizes, and initial sources so React takeover does not download a second image.
- Raw/standalone HTML: a real HTML parser resolves relative URLs against the output document and honors supported base URLs. Add responsive sources without breaking existing pictures, art direction, attributes, styles, alt text, anchors, or scripts. Never use regex to rewrite HTML. Existing custom pictures need explicit validation or migration, not nested pictures.
- CSS backgrounds: migrate content images to semantic markup where feasible; otherwise generate and validate explicit CSS variants. Decorative gradients remain untouched.
- Runtime galleries: thumbnail presentation uses derivatives; opening a full-resolution view retains the intended source, assigned only on the open interaction. Hidden dialogs must not contain an original image `src` or `srcset` that can fetch on initial load. Full-size downloads after interaction are explicitly outside thumbnail budgets. Verify image swaps clear stale responsive attributes.

Use accurate `sizes` values from layout contracts, with intrinsic width/height to reserve space. Header/LCP candidates stay eager and high priority where justified. Below-fold images default to lazy. Do not infer every first image is a hero or lazy-load an above-fold image blindly: establish role defaults per template and a small override for unusual layouts. This annotation controls presentation, not whether compression happens.

Provide `dev:optimized`: a watcher builds the complete pipeline to disk, including final HTML transformation and validation, then a local static server serves that final directory. Changes to images invalidate generation before rebuilding React/Hugo; content/template changes rerun the necessary later stages. Add/change/delete fixtures must update without restarting, with rebuilds serialized and failed builds not reported as fresh. Retain direct Hugo commands only as explicitly labeled fast authoring modes with no delivery-equivalence claim. `dev:optimized` is the canonical image verification path.

## 4. Make omissions fail the build

Add `test:images` and invoke its static production gate inside `npm run build`, so Netlify cannot skip it even when it does not run the full test suite. Include it in blog/recipe checks through their existing build dependency, and full CI. Avoid recursive build/test calls. Preserve `tests/test-command-contracts.test.js` browser-free blog/recipe build requirements: static output and source-policy checks block every canonical build; dedicated headless network/runtime checks run separately as required release validation for changes to image tooling, adapters, templates, runtime consumers, or image configuration. Establish that release check as a required CI status and verify its branch protection/deploy ordering before claiming unattended runtime enforcement. Until that enforcement is verified, report runtime validation as a release checklist requirement, not a Netlify build guarantee.

Validate actual final output: all local sources resolve within the publish root; selected variants exist and decode; descriptors match real widths; dimensions/aspect ratio are valid; no accidental enlargement; LCP roles are not lazy; shared manifest references and React/runtime consumers are covered. Prototype bounded AST rules against existing consumers before expanding them; enforce supported authoring APIs rather than attempting general JavaScript data-flow analysis. Add AST-based source rules across all first-party JS/TS/JSX/TSX and inline template scripts, not just registered adapters: only the shared component/adapter may create raster image nodes or assign image delivery URLs (`src`, `srcset`, `setAttribute`, image constructors, and injected HTML). Narrow reviewed exceptions identify exact consumers. New raw React `<img>` and unregistered runtime assignments must fail `npm run build`; unsupported dynamic image construction fails review rather than being claimed as exhaustively statically provable. Generated/vendor files have explicit separate treatment. Exercise the known runtime routes in the release checks. CSS and non-HTML entry points must have explicit coverage, not merely be invisible to the checker.

Provisional candidate budgets: 150 KB for hero candidates up to 800 pixels; 300 KB up to 1600; 100 KB for thumbnails up to 640. Also validate the actual selected response in explicit 390px/DPR1, 390px/DPR2, 1440px/DPR1, and 1440px/DPR2 viewport cases. Derive expected widths from the real rendered slot, sizes, source resolution, and ladder; DPR2 mobile is not assumed to select a candidate below 800. Inventory must set budgets for larger selected candidates before rollout. Calibrate against the full inventory and visual checks before freezing them; never degrade legibility to pass a byte limit. Exceptions must identify exact source/usage, reason, owner, and review date. Reject wildcard and expired exceptions. CI reports both failures and all exceptions.

Implementation is a later task. Before any authorized release, verify repository URL, intended branch, exact commit, remote state, and the Christmas deployment mapping. Source-byte and encoder-policy hashes invalidate the build cache.

This bounded alternative replaces the proposed retained-release bundle. Old tabs continue to resolve current-source variants after unrelated releases and same-path replacements; an old tab may show current artwork. Source deletion/rename or policy-family retirement is not retained. No unbounded storage or historical-image guarantee. Test old-page candidate URLs against a second clean release with unchanged/replaced sources and verify live revalidation headers. Preserve original/social URLs and the Christmas noindex subtree for new derivative paths. Rollback uses the previous verified deployment.


Local implementation is complete when a clean canonical build optimizes a newly added ordinary image without a manual command, all inventoried local rendering surfaces are covered, and bypass fixtures fail. Rollout readiness additionally requires verified release enforcement; unverified enforcement means rollout readiness remains pending.
